Lesson 10 · 安全边界的核心

沙箱：LLM 生成的代码在哪里执行

本课解剖 src/dataharness/sandbox/ 与 providers/sandbox/：为什么需要沙箱、OpenSandbox 如何被接入、attestation 探测与 digest 锁定如何保证「配置了才算数」。

1. 为什么必须有沙箱

项目最基本的威胁假设（ARCHITECTURE.md:22-24）：

  • LLM 生成的代码视为不可信输入 —— 它可能读文件、删文件、外传数据、跑死机器。
  • Host（你的电脑）绝不能直接执行它：禁止 exec/eval/import 任何生成代码（ARCHITECTURE.md:78）。

所以代码只能进隔离容器。项目用 OpenSandbox 平台 —— 它负责创建、资源限制、进程隔离，DataHarness 负责「用制度约束它」：把 spec 写死、创建后核验、不符就失败。

Host（可信） 沙箱（不可信） FastAPI / Worker secure-analysis 容器（Docker） │ │ └── SandboxProvider 协议 ────────────────┤ create / connect / execute / ├── /project 只读（Snapshot 文件） cancel / terminate ├── /task/working 可写（Task 中间数据） └── /task/staging 可写（待发布输出） 默认断网 · 非 root · 资源受限

2. 协议：业务层只看接口

业务代码只依赖 SandboxProvider 协议（sandbox/protocols.py:10-31）：

class SandboxProvider(Protocol):
    """Run-scoped Sandbox 生命周期；不提供 Host shell、装包或网络开关。"""
    async def create(self, spec: SandboxSpec) -> SandboxLease: ...
    async def connect(self, sandbox_id: str) -> SandboxLease: ...
    async def execute(self, lease: SandboxLease, request: ExecutionRequest) -> ExecutionResult: ...
    async def cancel(self, lease: SandboxLease, step_id: str) -> None: ...
    async def terminate(self, lease: SandboxLease) -> None: ...

协议上没有「装包」「开网络」「跑任意命令」—— 接口形状本身就限制了能力。实现有两个：OpenSandboxProvider（生产）和 FakeSandboxProvider（测试，不执行任何代码，providers/sandbox/fake.py:33-117）。

3. SandboxSpec：安全契约在构造时就锁死

sandbox/models.py:86-114 的校验器 —— 不满足安全要求的 spec 在调用 Provider 之前就构造失败：

@model_validator(mode="after")
def _validate_security_contract(self) -> SandboxSpec:
    """安全策略不接受开发期宽松值；不符的规格在调用 Provider 前直接失败。"""
    if self.runtime != "secure-analysis":
        raise ValueError("V1 仅允许 secure-analysis 运行时")
    if not _DIGEST.fullmatch(self.image_digest):          # sha256:64位hex
        raise ValueError("镜像必须使用锁定的 sha256 digest")
    if (self.network_enabled or self.privileged or not self.root_read_only
            or self.user != "sandbox"):
        raise ValueError("Sandbox 必须断网、非特权、只读根且使用 sandbox 用户")
    mounts = {item.target: item for item in self.mounts}
    if set(mounts) != {"/project", "/task/working", "/task/staging"}:
        raise ValueError("必须且只能挂载 project、working 和 staging 三个受控目录")
    ...

逐条翻译：

  • 运行时写死：只能是 secure-analysis；
  • 镜像 digest 锁定：格式必须是 sha256: + 64 位十六进制（models.py:13）—— 不允许 latest 标签，Docker 无法把未锁定的引用解析成可变镜像（ARCHITECTURE.md:321）；
  • 三不：不断网不行（网络开关、特权模式、非只读根、非 sandbox 用户一律拒绝）；
  • 挂载精确匹配：必须且只能挂载 /project（只读）、/task/working、/task/staging，且 source 引用必须精确绑定当前 Run 的快照与 Task。

生产 spec 的构造在 worker.py:72-113（_sandbox_factory）：

SandboxMount(source_ref=f"snapshot:{run.project_snapshot_id}", target="/project", read_only=True),
SandboxMount(source_ref=f"task:{run.task_id}:working", target="/task/working", read_only=False),
SandboxMount(source_ref=f"task:{run.task_id}:staging", target="/task/staging", read_only=False),

「snapshot:xxx」「task:xxx:working」是资源引用而不是主机路径 —— 主机路径只存在于 Worker 的 mount resolver（worker.py:34-69），并且解析后必须仍在 Workspace 根目录内（worker.py:64-68）。

4. 创建后必须核验：attestation

光在 spec 里写死没用 —— 谁知道容器实际跑起来是不是那个样子？所以 OpenSandboxProvider.create（providers/sandbox/opensandbox.py:98-113）创建后立刻做运行时探测，失败就销毁：

async def create(self, spec: SandboxSpec) -> SandboxLease:
    """创建后立即认证；认证失败时尽力销毁，绝不保留宽松 lease。"""
    sandbox_id = await self._client.create_sandbox(spec)
    try:
        await self._attest(sandbox_id, spec)      # 探测实际配置
    except Exception:
        await self._client.terminate_sandbox(sandbox_id)   # 不符 → 销毁
        raise
    lease = self._lease(sandbox_id, spec)
    self._leases[sandbox_id] = _LeaseState(lease, spec)

探测脚本在 opensandbox_sdk.py:59-123（_PROBE_SCRIPT），在容器内部运行，检查：运行用户/UID、NoNewPrivs、CapEff=0、根目录可写性、出站网络连通性、三个挂载的存在与读写性、cgroup 内存上限。每一项与 spec 不符都 fail closed（opensandbox_sdk.py:321-350）。

对比函数 _matches（opensandbox.py:64-75）：实际与预期逐字段相等，多一个挂载、少一个挂载都不行。失败是唯一的出口 —— 「宁可沙箱不可用，绝不静默降级」。

5. 执行：每步独立进程

execute（opensandbox.py:138-169）的几个细节：

  • 同一沙箱不能并发执行同一 Step（防止重复副作用，opensandbox.py:146-149）；
  • 输出大小超限 → SandboxOutputLimitError（opensandbox.py:156-158）；
  • finally 里必须 cleanup_step：清残留进程；清不掉则整个 lease 作废（opensandbox.py:165-169）。

执行细节在 opensandbox_sdk.py:354-433：代码写入 /task/working/{step_id}.py，作为独立进程运行，支持取消事件；SQL 走镜像内固定脚本 dataharness-sql-runner.py。

为什么「每步独立进程」这么重要

因为没有持久 REPL（ARCHITECTURE.md:296-298）：Step 之间不能依赖 Python 变量或后台进程 —— 每步从零开始，结果只能通过文件（staging）传递。这消灭了「上一步的副作用影响下一步」的隐式状态。

6. 挂载解析：白名单 + 路径校验

资源引用 → 主机路径的解析在 worker.py:34-69（_mount_resolver）：

  • 白名单只有三种引用：snapshot:{id}、task:{id}:working、task:{id}:staging；
  • 其他一律 PolicyDeniedError；
  • 解析后的路径必须仍在 Workspace 根内、存在且是目录（worker.py:64-68）。

所以即使沙箱有漏洞想读主机文件，它也没有路径可读 —— 它只知道三个挂载点。

7. 镜像怎么来的：构建与锁定

镜像在 sandbox-images/secure-analysis/：build.bat 拒绝未锁定的基础镜像、安装 requirements.lock 依赖、删除运行期 pip 和缓存、创建非 root sandbox 用户（uid 10001）、写入 build-evidence/image-digest.txt（README.md:138-151）。配置里的 [sandbox].image_digest 必须与它一致。发布前的 release_check.py --require-image 会核验证据（README.md:161-165）。

8. 练习

练习：读安全契约
  1. 打开 sandbox/models.py，把 _validate_security_contract 的每个 if 写进一张表：「条件 / 拒绝的威胁」。
  2. 打开 providers/sandbox/opensandbox.py 的 _attest 与 _matches，说出 attestation 与 spec 校验的分工（谁防「配置错误」，谁防「实际不符」）。
  3. 打开 worker.py 的 _mount_resolver（34-69 行），试着自己构造一个恶意引用（如 ../runtime.db 或 /etc/passwd），看它会被哪一行代码拒绝。

小测验：镜像引用为什么必须是 sha256 digest 而不能是 latest？

查看解析
latest 指向的内容会随推送变化 —— 你今天验证安全的镜像明天可能被替换成别的。name@sha256:… 锁定的是内容本身（ARCHITECTURE.md:321-322）。创建时 docker daemon 对 digest 引用的解析强制这一约束。

小测验：attestation 探测在什么时候执行？

查看解析
create 后立即 attest（opensandbox.py:98-113），connect 重连时也重新 attest（opensandbox.py:115-121）—— 崩溃恢复后重连的沙箱必须仍是原来那个配置。
