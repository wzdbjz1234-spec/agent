Lesson 06 · 状态与事实的守护者

存储层：SQLite、迁移、事务与 CAS

本课解剖 src/dataharness/storage/：SQLite 连接策略、迁移系统、UnitOfWork、仓储层 CAS、事件日志。这是理解「崩溃恢复」的前提。

1. 为什么用 SQLite

本项目是本地优先、单机单用户（ARCHITECTURE.md:9）。SQLite 是本地状态事实源的最简选择：单文件、零运维、支持事务、内置全文检索（FTS5）。

两个数据库各司其职（ARCHITECTURE.md:335-341）：

数据库位置内容谁可见
Runtime SQLiteruntime-data/runtime.dbProject/文件版本/Snapshot、Task/Run/Step 状态、事件、队列、lease只有 Host；Agent 和沙箱永远不可见
Privacy SQLiteruntime-data/privacy/{task_id}.db每 Task 的 PII 占位映射只有 Host；与 Runtime 物理分离（第 09 课）

2. 连接策略：每次连接都正确配置

storage/database.py 定义了两个连接工厂。先看公共配置（database.py:14-22）：

row_factory = sqlite3.Row              # 行可按下标或列名访问
PRAGMA foreign_keys = ON               # 外键约束生效（SQLite 默认关闭！）
PRAGMA busy_timeout = 5000             # 写锁等待 5 秒而不是立刻报错
PRAGMA journal_mode = WAL              # 预写日志：读写不互斥
PRAGMA synchronous = FULL              # 每次提交等数据落盘（防断电丢数据）

关键点：foreign_keys = ON 必须每个连接手动开 —— 不配置的话 SQLite 会静默忽略外键。连接用 isolation_level=None（自动提交模式），事务完全由代码显式控制。

RuntimeConnectionFactory.connect() 在首次连接时自动执行迁移（database.py:25-41）。PrivacyConnectionFactory（database.py:44-71）有个有趣的安全细节：它校验 task_id 不含路径分隔符（database.py:59-64），防止路径穿越 —— ID 直接拼文件名。

3. 迁移系统：数据库的版本管理

迁移文件是带编号的 SQL，放在 storage/migrations/：

0001_runtime.sql           # 初始 schema + 不可变触发器
0002_workspace_publications.sql   # 发布日志表
0003_orchestration.sql     # 重试、checkpoint 恢复列
0004_finding_coverage.sql  # findings 覆盖报告列
0005_agent_harness.sql     # sessions.project_id、prompt 引用列

执行器在 storage/migrate.py：

  • 编号必须连续 1..N（migrate.py:26-43），跳号直接报错 —— 防止「我本地跑过 3 没跑 4」之类的漂移。
  • 每个迁移在独立事务里执行（migrate.py:97-109），失败整体回滚。
  • 已应用版本按名字核对，防止「同样编号不同内容」被当作已应用（migrate.py:90-92）。

数据库层也是不可变性的第二道防线 —— 看 0001 里的触发器（0001_runtime.sql:247-282）：

-- Snapshot 及其成员是追加式事实；任何更新或删除都意味着既有 Run 的数据视图漂移。
CREATE TRIGGER project_snapshots_no_update BEFORE UPDATE ON project_snapshots
BEGIN SELECT RAISE(ABORT, 'project_snapshots 不可更新'); END;

领域层 frozen（第 05 课）管「代码里改不了」，SQLite 触发器管「数据库里改不了」——两层保险。

4. UnitOfWork：一个事务干完所有事

storage/uow.py 是事务上下文管理器（uow.py:19-34）：

def __enter__(self) -> UnitOfWork:        # BEGIN（延迟）或 BEGIN IMMEDIATE
    connection.execute("BEGIN IMMEDIATE" if self._immediate else "BEGIN")
def __exit__(...):                        # 成功 commit，异常 rollback

典型用法 —— 仓储方法从不自己 commit，而是共享调用方的 UoW（repository.py:4-5）：

with self._store.unit_of_work() as uow:
    stored = uow.repo.get_run(claimed.run.id)
    updated = stored.value.succeed(now)
    uow.repo.save_run(updated, stored.version, "RUN_SUCCEEDED", lease=..., lease_checked_at=now)

「状态变更 + 审计事件 + 相关记录」在同一事务里成功或一起回滚 —— 不会出现「状态改了但事件丢了」。

immediate=True 用于队列领取（第 11 课）：先拿写锁再读候选，两个 Worker 不会同时领到同一个 Run（uow.py:13-17）。

5. 仓储层：行 ↔ 对象 + CAS

RuntimeRepository（repository.py，1225 行）是所有表访问的唯一入口。它的核心模式是 CAS（Compare-And-Swap）：每个表都有 row_version 列，每次更新都带版本条件：

# repository.py:1206-1209
def _require_cas(result) -> None:
    if result.rowcount != 1:
        raise ConcurrencyConflictError(...)

例如 save_task（repository.py:596-625）的更新条件：

UPDATE tasks SET status=?, ..., row_version = row_version + 1
WHERE id = ? AND row_version = ? AND status = ?

如果两个请求同时改同一个 Task，第二个的 row_version 已经不匹配，更新 0 行 → 抛 ConcurrencyConflictError。乐观并发控制：不加锁也能防止丢失更新。

仓储还复验状态机（repository.py:112-117）：即使调用方绕过领域层直接拼对象，_check_transition 也会在写库前拒绝非法转移 —— 领域校验的兜底副本。

6. 事件日志：追加式的审计事实

每次状态变更都伴随一个事件（同一事务）。append_event（repository.py:126-155）有两个安全特性：

# 拒绝把敏感内容写进事件
_FORBIDDEN_EVENT_KEY_PARTS = ("secret", "password", "token", "api_key", "pii", "prompt", "response", "payload")
_MAX_EVENT_PAYLOAD_BYTES = 16 * 1024

键名里含 secret/prompt/pii... 的元数据直接拒绝；payload 超 16 KiB 拒绝。所以事件流天然是脱敏的——第 13 课的 SSE 前端看到的就是这些事件。

事件的持久化消费方式：API 端 task_events 把 Task 及其所有 Run/Step/Finding 的事件按 ID 合并排序（api/services.py:343-355），SSE 用事件 ID 做游标断点续传（api/app.py:268-302）。

7. 队列原语：SQLite 当消息队列用

SqliteRuntimeStore 提供 5 个「原子队列操作」（store.py:17-22），每个都是完整事务：

方法行为行号
claim_next_run原子领取最早 QUEUED Run 或回收过期 RUNNING leasestore.py:34-100
heartbeat续租（校验 owner/epoch/未过期）store.py:102-126
request_cancel三种状态的取消语义（QUEUED 直接取消/WAITING 先恢复再取消/RUNNING 只记意图）store.py:128-151
resume_waiting恢复 WAITING 的 Run 并设置再试时间store.py:153-163
schedule_retry释放 lease + 记录重试次数 + 设置 next_attempt_at，同一事务store.py:165-206

为什么要封装成「完整事务原语」而不是公开方法？看注释（store.py:17-22）：调用方无法在「选候选」和「写 lease」之间插入不原子逻辑 —— 排队语义被锁死在正确的地方。

小测验：WAL 模式的直接好处是？

查看解析
WAL（Write-Ahead Logging）让写操作先追加到 wal 文件，读操作继续读旧快照 —— 读写互不阻塞（database.py:14-22）。API 读、Worker 写同一 SQLite 时，这非常关键。

小测验：两个 Worker 同时 claim 同一个 Run 会发生什么？

查看解析
claim_next_run（store.py:34-100）用 BEGIN IMMEDIATE 串行化，WHERE row_version = ? 保证只有第一个提交者成功（CAS）。失败者抛 LeaseLostError，Worker 循环继续领下一个。第 11 课详讲 lease 语义。
