Lesson 12 · 让模型结论可信

验证门与血缘：结论如何被证明

本课解剖 analysis/verification.py 与 domain/finding.py、domain/lineage.py：Agent 提交的结论凭什么可信？答案：必须过三个 Host 验证门，并且每条结论都有可追溯的血缘链。

1. 问题的本质：模型不能自证

LLM 会一本正经地胡说八道。所以项目的规则是（ARCHITECTURE.md:536-539）：

每个最终 Finding 是结构化对象；至少引用一个属于当前 ProjectSnapshot 与 Task/Run 的有效证据； 证据可追溯到文件的页码/段落/工作表/行范围，或 AnalysisStep、输入 Dataset、代码、Artifact；内容 hash 未变化。

结论（Finding）由 Agent 提出，由 Host 验证。第 05 课讲过 FindingCandidate → Finding 的两阶段；本课看验证怎么做。

2. 三个 Gate

VerificationService.verify（analysis/verification.py:290-346）对每个 DRAFT Finding 依次跑三个门：

execution_reports = tuple(self._execution.check(item) for item in summaries_tuple)   # ① 执行门
integrity_reports = tuple(self._integrity.check(run, item) for item in summaries_tuple)  # ② 完整性门
reports = (*execution_reports, *integrity_reports, self._evidence.check(finding))    # ③ 证据门
failed = any(not report.passed for report in reports)
if failed:
    updated = finding.reject(); event = "FINDING_REJECTED"        # 任何一门不过 → 拒绝
elif warnings:
    updated = finding.mark_warning(); event = "FINDING_WARNING"   # 有数据质量警告 → WARNING
else:
    updated = finding.verify(); event = "FINDING_VERIFIED"        # 全过 → 正式结论

ExecutionGate：执行过程正常吗（verification.py:72-86）

  • 引用的 AnalysisStep 状态是 SUCCEEDED；
  • 退出码正常；
  • 输出元数据完整（没有超时/取消/资源耗尽）。

IntegrityGate：数据没被动过（verification.py:89-172）

  • 从数据库重新读 Run/Snapshot/Step，重新验证输入文件 hash（重新打开原件比对）；
  • 对发布产物重新计算 hash，与注册记录比对大小与 hash；
  • 简单说：所有 hash 从头再算一遍，任何不一致 = CORRUPT。

EvidenceGate：结论有证据吗（verification.py:175-272）

  • Finding 的 Task/Run/Snapshot 归属正确；
  • 每条证据（FILE/STEP/DATASET/ARTIFACT，domain/finding.py:22-28）在数据库中真实存在、hash 匹配；
  • 覆盖报告的快照一致；覆盖缺口变成披露（notice）而不是拒绝 —— 诚实披露缺口（verification.py:324-345 的事件 FINDING_COVERAGE_NOTICE）。

3. 数据质量警告：不阻断但披露

DataWarningDetector（analysis/warnings.py）从沙箱统计信息检测 5 类数据问题：行数异常变化、Join 膨胀、缺失值、类型转换失败、重复值（ARCHITECTURE.md:539）。检测到 → Finding 标 WARNING（不拒绝），事件 FINDING_DATA_WARNINGS 会变成 API 回答里的 disclosures（api/services.py:400-409）。

为什么不把警告也变成拒绝？

因为「数据本身有质量问题」≠「分析结论错」。系统诚实标注「此结论基于有缺失值的数据」，把判断权交给用户 —— 而不是假装自己是统计裁判（ARCHITECTURE.md:539）。

4. 血缘：每个产物从哪来

发布 Dataset/Artifact 时，AnalysisRuntime 同时写血缘记录（analysis/runtime.py:335-377）：

# 输入文件版本 → 输出 Dataset 的血缘边
Lineage(run_id=..., source=ResourceRef(kind=ResourceKind.FILE_VERSION, resource_id=..., content_hash=...),
        target=ResourceRef(kind=ResourceKind.DATASET, resource_id=..., content_hash=...), created_at=...)
# 执行 Step（带代码 hash）→ 输出
Lineage(run_id=..., source=ResourceRef(kind=ResourceKind.STEP, resource_id=...), target=...)

资源类型共 5 种（domain/lineage.py:17-24）：FILE_VERSION / STEP / DATASET / ARTIFACT / FINDING。血缘边用稳定 ID + hash，绝不用原始路径（domain/lineage.py:37-46）。查询：GET /tasks/{id}/lineage（api/app.py:325）。

有了血缘，就能回答「这个图表是哪些文件、哪段代码算出来的」—— 这是审计与复现的基础。

5. 回答的披露：disclosures 字段

最终回答 TaskAnswer（api/models.py:58-76）有一个特别字段 disclosures：来自覆盖缺口与数据质量事件，让客户端能区分「正常结论」和「需要人工复核」。第 13 课你会真的看到它。

6. 练习

练习：追一条证据链
  1. 打开 domain/finding.py 的 EvidenceRef（31-40 行），列出它的四个字段，说出每个字段在 EvidenceGate 里被怎么用。
  2. 读 analysis/verification.py 的 IntegrityGate.check（89-172 行），找出它「重新打开文件比对 hash」的代码位置（用到 corpus 的哪个方法？）。
  3. 打开 analysis/warnings.py，数出 5 类警告种类，并说明它们的数据来源（沙箱的什么输出？）。

小测验：Agent 提交的 Finding 缺证据，最终状态是？

查看解析
EvidenceRef 要求非空证据（构造时校验，domain/finding.py:56-61），且 EvidenceGate 会逐条核验（verification.py:175-272）。任何一门失败 → finding.reject()，DRAFT 直接变 REJECTED（verification.py:302-304）。

小测验：完整性门（IntegrityGate）在验证什么？

查看解析
IntegrityGate（verification.py:89-172）是「内容寻址」的应用：结论依赖的每一样东西的 hash 与注册值一致，保证「你看到的证据就是分析时的证据」。
