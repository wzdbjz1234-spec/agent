Lesson 08 · 项目的智能核心

Agent 基础：LLM 如何调用工具

本课讲解 Agent 的概念与工作循环，然后解剖 src/dataharness/agent/：装配、工具、结构化输出、Runner。学完你就能理解「模型是怎么一步步完成分析的」。

1. Agent 是什么

一个普通 LLM 只会「你问一句，它答一句」。Agent（智能体）= LLM + 工具 + 循环：模型可以在对话中请求调用工具（比如搜文件、执行代码），拿到结果后继续思考，直到得出结论。循环长这样：

用户问题 │ ▼ ┌──────────────────────────────┐ │ Agent 循环（PydanticAI 负责）│ │ 1. 模型：根据上下文决定下一步 │ │ - 要么输出最终答案 │ │ - 要么请求调用某个工具 │ │ 2. 执行工具 → 结果回填对话 │ │ 3. 回到 1 │ └──────────────────────────────┘ │ ▼ 最终答案（结构化 JSON）

PydanticAI 是这个循环的官方实现（依赖声明 pyproject.toml:14）。项目自己的代码不做第二套 Agent Loop —— 它只负责装配与约束（ARCHITECTURE.md:155-158）。

2. 装配：create_agent

整个项目只有一个 Agent（ARCHITECTURE.md:688-691）。它的装配函数在 agent/assembly.py:41-88：

def create_agent(
    *,
    gateway: ModelGateway,
    task_id: TaskId,
    run_id: RunId | None = None,
    skills: SkillRegistry,
    active_skills: tuple[tuple[str, ContentHash | None], ...] = (),
    memory: MemoryCapability | None = None,
) -> Agent[AgentDependencies, AgentFinalOutput]:
    """组装单一 PydanticAI Agent，并仅注册固定的窄工具。"""
    tools = [
        list_project_files, search_project, inspect_project_file,
        get_project_coverage, execute_python, execute_sql,
        preview_project_table, publish_chart, inspect_output, submit_finding,
    ]
    if loaded:
        tools.append(run_skill_script)
    if memory is not None:
        tools.append(search_history)
    instructions = (
        "你是 DataHarness 的唯一分析 Agent。只能使用注册的窄工具；"
        "不要访问主机路径、直接执行代码、安装依赖或创建第二个 Agent。"
        "最终必须输出结构化 JSON，status 只能是 COMPLETED 或 WAITING；"
        "无论 status 如何，都必须使用 answer 字段承载面向用户的说明…"
    )
    return Agent(
        gateway_function_model(gateway, task_id, run_id),   # 模型：接 ModelGateway
        output_type=AgentFinalOutput,                        # 输出必须是这个结构
        deps_type=AgentDependencies,                         # 依赖：运行时要注入的对象
        system_prompt=instructions,
        tools=tools,
        retries=1,                                           # 模型错误最多重试 1 次
        name="dataharness-agent",
    )

逐项拆解：

  • 模型：gateway_function_model(...) 把 ModelGateway 包装成 PydanticAI 认识的 FunctionModel（agent/model.py:71-90）—— 所有模型流量都强制走隐私网关（第 09 课）。
  • 输出类型：AgentFinalOutput（agent/models.py:21-52）强制模型最后输出 status + answer + references + unresolved_issues 的结构化 JSON。
  • 依赖：AgentDependencies（agent/models.py:55-73）是工具能拿到的运行时对象包：AnalysisRuntime、SkillRegistry、ModelGateway、checkpoint 管理器等。
  • 系统提示词：硬性约束。「只能使用注册的窄工具；不要访问主机路径、直接执行代码…」。注意最后一句：即使 WAITING 也要写 answer —— 这是和 DeepSeek 风格模型兼容的细节（models.py:31-52 有对应的解析兼容逻辑）。

预算也是装配的一部分（assembly.py:91-93）：

def default_usage_limits() -> UsageLimits:
    return UsageLimits(request_limit=20, tool_calls_limit=40, total_tokens_limit=50_000)

一次 Run 最多 20 次模型请求、40 次工具调用、5 万 token —— 这就是「预算与失控控制」的第一层（ARCHITECTURE.md:541-551）。

3. 工具：模型能做什么，全由我们定

工具定义在 agent/tools.py。每个工具是一个 async 函数，第一个参数是 ctx: RunContext[AgentDependencies]（PydanticAI 的约定），后续是模型传入的参数。看最有代表性的两个：

# tools.py:73-84  —— 检索工具
async def search_project(ctx: RunContext[AgentDependencies], query: str, limit: int = 20) -> str:
    """ProjectCorpus FTS5/BM25 检索；回答只能引用实际返回的文件版本。"""
    ...

# tools.py:114-149 —— 执行代码工具
async def execute_python(
    ctx: RunContext[AgentDependencies],
    code: str,
    inputs: tuple[InputReference, ...] = (),
    expected_outputs: tuple[OutputSpec, ...] = (),
    timeout_seconds: int = 300,
    budget_units: int = 1,
) -> str:
    """生成代码经 AnalysisRuntime 在 OpenSandbox 执行；Host 不 exec 任何代码。"""
    ...

完整工具表（ARCHITECTURE.md:303-316）：

工具干什么代码位置
list_project_files列出快照里的文件版本tools.py:60
search_project全文检索相关片段tools.py:73
inspect_project_file有界读取文件内容（默认 4096 字符）tools.py:86
get_project_coverageFULL_PROJECT 覆盖报告tools.py:101

「窄工具」原则

不给模型：通用 shell、安装包、外部 API、浏览器、邮件、在线数据库（ARCHITECTURE.md:316-317）。 模型的能力边界由工具清单精确划定 —— 工具越少，出错和越界的可能性越小。

每个工具的返回都经过统一出口（tools.py:17-28）：

text = json.dumps(payload, ensure_ascii=False, default=str, sort_keys=True)
return ctx.deps.gateway.sanitize_tool_result(ctx.deps.task_id, text).cloud_text

工具结果在回填给模型之前，也要过 ModelGateway 的脱敏（第 09 课）。

4. 工具结果太长怎么办：有界化

模型上下文有限，工具结果不能无限大。项目的策略（ARCHITECTURE.md:405）：大结果写进 Workspace，只给模型有界内容或引用。例子：inspect_project_file 的 max_chars=4096（tools.py:86-100）；执行代码的 stdout/stderr 在 AnalysisSummary 里被截断（max_summary_chars，analysis/runtime.py:435-471）。

5. 一次 Run 的 Agent 流程：AgentRunHandler

把装配串起来的是 AgentRunHandler.__call__（agent/handler.py:140-319），它是第 11 课 Worker 调用的「Run 处理器」。流程：

  1. 校验不可变的 PROMPT.json（prompt_ref/hash 对得上，handler.py:74-96）；
  2. 闲聊检测：问候语直接本地回复，不调模型（handler.py:150-154，agent/intent.py）；
  3. 依赖门：沙箱/发布桥缺失 → WAITING(MISSING_DEPENDENCY)（handler.py:155-166）；
  4. 装配 ContextCheckpointManager、MemoryCapability、AnalysisRuntime 与 Dependencies（handler.py:176-220）；
  5. AgentRunner.run(...) 执行 Agent 循环（handler.py:236）；
  6. 错误映射：预算耗尽→WAITING(BUDGET_EXHAUSTED)、模型配置问题→WAITING(MISSING_DEPENDENCY)、模型输出异常→WAITING、检测到凭据→WAITING(POLICY_DENIED)（handler.py:237-274）；
  7. 成功：写脱敏 ANSWER.json → 记忆 → 验证门处理 DRAFT Finding → 返回 RunOutcome（handler.py:286-319）。

关键点：Agent 自己决定不了 Run 的命运 —— 它只能产出「成功/等待」，最终状态由 Host（执行器）落库（第 11 课）。

6. Runner 与 Checkpoint：长任务怎么不丢记忆

AgentRunner.run（agent/runner.py:34-109）做了三件事：

  1. 恢复：从最近 checkpoint 恢复消息历史（崩溃后继续，不从头再来）；
  2. 运行：self._agent.run(...)，用完预算则保存未决问题后抛 AgentBudgetExhausted（runner.py:59-70）；
  3. 保存：成功后写完整消息 checkpoint；若序列化超过 context_budget_chars（默认 120,000），触发 Compaction —— 用模型把历史压缩成摘要（runner.py:90-104，agent/context.py:199-242）。

Checkpoint 物理存放：消息内容在 Workspace 文件（state/checkpoints/checkpoint-{sequence}.json），元数据（run_id、hash、快照、沙箱、lease epoch）在 Runtime SQLite 的 checkpoint_metadata 表（agent/context.py:114-146）。恢复时校验 hash 与快照绑定（agent/context.py:148-171）。第 11 课的「恢复决策」就靠它。

7. 练习

练习：读工具实现
  1. 打开 agent/tools.py，读 submit_finding（248 行附近）完整实现，找出它如何构造 FindingCandidate 并记录「模型请求了验证」。
  2. 读 agent/intent.py 的 classify_prompt，理解「闲聊短接」的判定条件。
  3. 打开 agent/models.py，说出 AgentFinalOutput 的每个字段及其约束（min/max）。
  4. 思考题：为什么系统提示词里写「checkpoint summary 只是摘要，不是事实」？读完 runner.py:90-104 后回答。

小测验：Agent 的「能力边界」由什么决定？

查看解析
assembly.py:54-69：模型只能调用注册的工具。不给通用 shell、不装包、不联网，模型就「无计可施」——这是硬边界，比提示词约束可靠。

小测验：Agent 输出 status=WAITING 时，Run 会怎样？

查看解析
WAITING + wait_reason（第 05 课的不变量！）意味着「卡住了，需要外部介入」——用户补充信息（USER_INPUT）、预算耗尽（BUDGET_EXHAUSTED）、缺依赖（MISSING_DEPENDENCY）等（handler.py:237-274）。恢复由第 11 课的 resume 机制处理。
