Lesson 07 · 数据的入口

文件导入、全文检索与快照：ProjectCorpus

本课解剖 src/dataharness/projects/：一条上传的文件如何变成「可被 Agent 检索的只读快照」。这是 Agent 分析的原材料来源。

1. ProjectCorpus 是什么

它是「项目的语料库」，一个 deep module（深模块）：对外只暴露几个小方法（ARCHITECTURE.md:159-162），内部封装了文件导入、格式提取、全文索引、快照、检索全部复杂度：

import_files / create_snapshot / search / open_resource / full_project_coverage / ...

对应的类在 projects/corpus.py（约 355 行），用到的三个兄弟模块：

  • projects/extractors.py —— 识别真实格式并提取文本/元数据；
  • projects/index.py —— 每项目一个 SQLite FTS5/BM25 全文索引；
  • providers/workspace/local.py —— 受控的文件落地（第 10 课还会用到它的路径策略）。

2. 导入管线：一条文件的生命线

核心在 corpus.import_file（corpus.py:91-161），先看全景（ARCHITECTURE.md:251-260）：

upload -> validate real type / size / path （sniff_media_type 看魔数，不信扩展名） -> immutable ProjectFileVersion + SHA-256 （sources/ 下只读保存） -> local extraction （PDF/Excel/Word… -> 可定位文本块） -> FTS5/BM25 + metadata index （indexes/corpus.sqlite3） -> READY | FAILED | UNSUPPORTED （最终状态，不可再改）

代码分两段。第一段：在 UoW 里登记文件与版本（corpus.py:93-107）：

project = uow.repo.get_project(project_id).value
if project.status != ProjectStatus.ACTIVE:
    raise ValueError("归档项目不能导入新文件")
current = next((item for item in uow.repo.list_project_files(project_id)
                if item.name == normalized_name), None)
if current is None:
    current = ProjectFile(...); uow.repo.add_file(current); version_number = 1
else:
    version_number = len(uow.repo.list_file_versions(current.id)) + 1   # 同名 = 新版本
version = ProjectFileVersion(...)
uow.repo.add_file_version(version)
  • 归档项目拒绝新文件 —— 归档只禁止新输入，不破坏历史（ARCHITECTURE.md:411-412）。
  • 同名上传 = 新版本（version_number+1），绝不覆盖旧版本 —— 旧 Run 的输入视图不漂移。

第二段：真实的 I/O 管线，任何异常都收敛到终态（corpus.py:109-150）：

try:
    self._workspace.import_source(project_id, current.id, version.id, source, normalized_name, content_hash)
    stored_path = self._workspace.source_path(...)
    media_type = sniff_media_type(stored_path)          # 看魔数，不信扩展名
    document = extract_document(stored_path, content_hash, media_type)
    self._write_extracted(project_id, version.id, document)
    CorpusIndex(self._workspace.index_path(project_id), self._max_snippet_chars).replace(
        file_id=current.id, file_version_id=version.id, file_name=normalized_name, document=document)
    final = version.mark_ready(content_hash, size, media_type, at=self._clock())
except UnsupportedFormatError:
    final = version.mark_unsupported(at=self._clock())
except Exception:
    final = version.mark_failed(at=self._clock())

顺序有讲究（ARCHITECTURE.md:260）：先保存不可变原件（解析崩溃也不丢输入），再提取、再索引；提取物和索引是「可重建的派生数据」，丢了可以用原件重建（rebuild_derived，corpus.py:250-279）。

3. 格式识别：相信魔数，不相信扩展名

sniff_media_type（extractors.py:53-87）的逻辑：

  • 先看魔数（文件头部字节）：%PDF- 是 PDF、PAR1 是 parquet、SQLite format 3\0 是 SQLite、DUCK 是 DuckDB（extractors.py:53-87）。
  • Office 格式（xlsx/docx/pptx）本质是 ZIP，检查 ZIP 容器内的结构。
  • JSON/CSV/Markdown/纯文本只能按扩展名。
  • 都不认识 → UnsupportedFormatError → 版本标记 UNSUPPORTED，不假装已分析（ARCHITECTURE.md:249）。

为什么不信扩展名？因为用户可以上传「改名成 .txt 的 PDF」，按扩展名走会解析失败或误判。

支持的 11 种提取器（extractors.py:261-273）输出 ExtractedDocument：文本被切成带定位信息的 TextChunk —— 段落号、页码、工作表+行范围、幻灯片号（ARCHITECTURE.md:247-249）。定位信息是第 12 课 EvidenceGate 的根基：结论要能指向「第 3 页第 2 段」。提取器版本号 EXTRACTOR_VERSION = "builtin-v1"（extractors.py:23）绑定到每个提取物，升级提取器后旧索引可整体重建。

4. FTS5/BM25 全文索引

每个 Project 一个索引文件 indexes/corpus.sqlite3，结构（index.py:21-36）：

CREATE VIRTUAL TABLE IF NOT EXISTS chunks USING fts5(
    file_version_id UNINDEXED, locator_json UNINDEXED, text, metadata_json UNINDEXED,
    tokenize='unicode61');

FTS5 是 SQLite 内置的全文检索虚拟表：text 列会被分词建倒排索引。检索函数 search()（index.py:88-139）：

SELECT metadata.file_id, chunks.file_version_id, metadata.file_name,
       metadata.source_hash, metadata.media_type, chunks.text, chunks.locator_json,
       bm25(chunks) AS rank
FROM chunks JOIN index_metadata AS metadata
  ON metadata.file_version_id = chunks.file_version_id
WHERE {clauses}
ORDER BY rank, chunks.rowid LIMIT ?
  • bm25(chunks) 是 BM25 相关度评分（值越小越相关，所以 score=-float(row["rank"]) 取负转成正的相似度，index.py:139）。
  • 检索范围被限制在 Snapshot 的 READY 成员里（corpus.py:235-248）——查的是「固定视图」，不是「最新文件」。
  • unicode61 分词器支持中文等非英文文本。
  • 调参（BM25 的 k1/b）在配置里：[index] bm25_k1 = 1.2, bm25_b = 0.75（config.py:110-117）。

项目刻意不用向量数据库做跨文件检索 —— 结构化数据走 DuckDB，文档用本地全文检索（ARCHITECTURE.md:273），少一个重依赖。

5. 不可变快照：Run 的输入视图

create_snapshot（corpus.py:186-233）把「每个逻辑文件的最新版本」固化成 ProjectSnapshot：

snapshot = ProjectSnapshot(
    id=SnapshotId(self._ids.new("snapshot")),
    project_id=project.id, created_at=self._clock(),
    entries=tuple(SnapshotEntry(...) for item in versions),      # 所有版本，含 FAILED/UNSUPPORTED
    index_version=INDEX_VERSION if any(v.status == FileVersionStatus.READY for v in versions) else None,
    dataset_version_ids=tuple(item.id for item in datasets),
)

随后 materialize_snapshot 把 READY 文件复制到 snapshots/{snapshot_id}/ 下，作为沙箱只读挂载的源（corpus.py:219-232、providers/workspace/local.py:202-230）。

为什么 Run 必须绑定快照而不是直接用最新文件？

可复现性。Run 开始后你又上传了新文件 —— 旧 Run 的分析必须不受影响（ARCHITECTURE.md:262-264）。快照创建后不可变（第 05/06 课的两层保险），崩溃恢复也用同一快照。想要新文件？创建新 Run 和新快照。

6. 两种检索模式：RELEVANT 与 FULL_PROJECT

Agent 有两种「看文件」的方式（ARCHITECTURE.md:266-272）：

模式行为回答的要求
RELEVANT用 FTS5/BM25 找相关片段只能声称使用了实际引用的文件
FULL_PROJECT枚举快照全部文件，分批提取/分析，生成 ProjectCoverageReport必须绑定覆盖报告；存在 FAILED/UNSUPPORTED/SKIPPED 项时必须披露缺口

覆盖报告的生成在 full_project_coverage（corpus.py:317-355），数据模型是 ProjectCoverageReport（domain/project.py:176-212），它有个 has_uncovered() 方法 —— 第 12 课会看到它如何变成回答里的「披露」。

7. 练习

练习：亲手导入一个文件
  1. 启动服务 uv run dataharness serve。
  2. 建项目、上传一个 CSV（用 README.md:266-286 的 curl 命令）。
  3. 用 Invoke-RestMethod "http://127.0.0.1:8000/projects/…/files" 看文件状态 —— 应该是 READY。
  4. 在 runtime-data/projects/{id}/ 下找到 sources/extracted/indexes 目录，确认三种产物都存在。把 extracted 里的 JSON 打开看看 chunk 的定位信息长什么样。

小测验：同名文件再次上传会发生什么？

查看解析
corpus.py:98-107：version_number + 1，旧版本文件在 sources/ 下永远保留（只读、不可变）。「禁止覆盖或删除被 Snapshot 引用的版本」（ARCHITECTURE.md:242）。

小测验：一个内容异常的文件（如损坏的 PDF）导入后会怎样？

查看解析
先保存原件再解析（corpus.py:109-150），失败落到 FAILED 终态；FULL_PROJECT 覆盖报告必须列出它。诚实记录「分析不了」比假装分析完更符合项目的「不假装」原则。
