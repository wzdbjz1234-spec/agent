Lesson 11 · 崩溃恢复与并发安全

耐久编排：Worker、租约、重试与崩溃恢复

本课解剖 providers/durable/executor.py 与 storage/store.py 的队列原语：任务如何被领取、如何保证只有一个 Worker 在跑、崩溃后如何恢复。这是「长时运行 Agent」项目的精髓。

1. 问题：Agent 任务需要"耐久"

一个分析 Run 可能跑几十分钟。期间可能发生：API 重启、Worker 崩溃、沙箱被销毁、机器断电。用户的期望（ARCHITECTURE.md:483-484）：

  • 任务不丢：状态都在 SQLite 里，随时可恢复；
  • 不重复执行：恢复后从最后 checkpoint 继续，而不是重跑全部；
  • 同一时间只有一个 Worker 在跑同一个 Run（否则会重复执行代码、重复发布产物）。

实现方案：SQLite 即队列 + 租约（lease）+ fencing token，不用 Prefect 之类的重型编排（ARCHITECTURE.md:474）。

2. 领取：原子操作

Worker 的循环（executor.py:110-120）：

async def run_worker(self, stop_event: asyncio.Event, *, idle_sleep_seconds: float = 0.1) -> None:
    """可停止的 worker loop；等待期间不持有任何 Run lease。"""
    while not stop_event.is_set():
        result = await self.run_once()     # 领取并执行一个 Run
        if result is None:
            await asyncio.wait_for(stop_event.wait(), idle_sleep_seconds)   # 空闲就睡 0.1s

领取本身是 SQLite 原子事务 claim_next_run（store.py:34-100），选择条件值得逐行读：

SELECT * FROM runs WHERE
  (status = 'QUEUED' AND (next_attempt_at IS NULL OR next_attempt_at <= ?))      -- ① 排队的
  OR (status = 'RUNNING' AND
      ((lease_owner IS NOT NULL AND lease_expires_at <= ?)                       -- ② 租约过期的
       OR (lease_owner IS NULL AND next_attempt_at IS NOT NULL AND next_attempt_at <= ?)))  -- ③ 重试到期的
ORDER BY CASE WHEN status = 'QUEUED' THEN 0 ELSE 1 END, created_at, id LIMIT 1

① 优先领最早排队的；②回收租约已过期的 RUNNING Run —— 这正是一个「跑死了但没交代的 Run」，它的 lease 过期等于宣告死亡；③ 领重试时间已到的。整个领取 + 写 lease + 发事件在一个 BEGIN IMMEDIATE 事务里（第 06 课），并发安全。

3. 租约与 fencing：谁在跑，由令牌说了算

领取时执行器写：lease_owner、lease_epoch = lease_epoch + 1、lease_expires_at、heartbeat_at（store.py:63-71）。

之后每一次状态提交（save_run，repository.py:705-723）都带租约条件：

where += " AND lease_owner = ? AND lease_epoch = ? AND lease_expires_at > ?"

只有「当前 owner + 当前 epoch + 未过期」才能提交。这就是 fencing token 模式：

为什么 epoch 是关键

假设 Worker A 领取 Run（epoch=1）后网络卡了 40 秒（lease 30 秒过期）。Worker B 回收了它（epoch=2）开始执行。 这时 A 醒了想提交结果 —— 它的 epoch=1 已经与库里的 2 不匹配，提交被拒（LeaseLostError）。 只有当前持有者能说话，过期者永远闭嘴。这防止了「僵尸 Worker 覆盖活 Worker」的最坏并发事故。

注意 expires_at 的判断用的是数据库里存的过期时间而不是调用方传的时间（repository.py:710-711 的注释）—— 即使 lease「已过期但还没被回收」，旧 Worker 也提交不了。lease 到期本身就构成边界。

4. 执行与恢复决策

执行入口 _execute_claim（executor.py:122-170）。先看恢复决策（executor.py:176-192）：

@staticmethod
def _recovery_decision(run, recovered, checkpoint) -> RecoveryDecision:
    if run.status in (RunStatus.SUCCEEDED, RunStatus.FAILED, RunStatus.CANCELLED):
        return RecoveryDecision.TERMINAL          # 终态：什么都不做
    if not recovered:
        return RecoveryDecision.START_FROM_BEGINNING   # 新 Run：从头开始
    if checkpoint is None:
        return RecoveryDecision.START_FROM_BEGINNING   # 恢复但无 checkpoint：从头
    if checkpoint.project_snapshot_id != run.project_snapshot_id:
        raise PolicyDeniedError(...)                   # checkpoint 与快照不符：拒绝
    return (RecoveryDecision.RESUME_FROM_CHECKPOINT if checkpoint.sandbox_id
            else RecoveryDecision.REBUILD_SANDBOX)     # 有沙箱可重连就续跑，否则重建沙箱续跑

四个决策的含义：

决策场景行为
TERMINALRun 已是终态不执行
START_FROM_BEGINNING新 Run 或没有任何 checkpoint从头跑
RESUME_FROM_CHECKPOINT有 checkpoint 且沙箱还在重连沙箱 + 恢复消息历史，继续
REBUILD_SANDBOX有 checkpoint 但沙箱没了重建沙箱（同 digest）+ 恢复，继续

恢复前还有两道防线：checkpoint 的镜像 digest 必须与当前 spec 一致（executor.py:202-208），重连的沙箱 lease 上下文必须与 Run 完全一致（project/task/snapshot/digest，executor.py:214-223）。恢复绝不静默换镜像或换快照。

沙箱采用按需创建：只在工具第一次需要时才创建（executor.py:138-145）—— 纯闲聊的 Run 可能根本不需要沙箱。

5. 失败重试：有限次 + 退避

_handle_failure（executor.py:318-340）：

failure_class, retryable = classify_error(error)      # 错误分类（第 5 小节）
if retryable and attempts < self._max_retries:
    delay = timedelta(seconds=self._backoff_base * (2**attempts))   # 指数退避
    self._store.schedule_retry(claimed.lease, attempt=attempts + 1,
                               failure_kind=failure_class, delay=delay, now=self._clock())
    return self._get_run(claimed.run.id)
if retryable and attempts >= self._max_retries:
    error = RetryLimitExceeded(f"Run 自动重试达到上限：{self._max_retries}")
return self._fail_claim(claimed, error, failure_class, cause=root_error)
  • 哪些错可重试：只有模型超时/上游错误/限流、沙箱超时/输出超限/沙箱丢失（orchestration/errors.py:65-84）。策略拒绝、凭据阻断这类错误不可重试 —— 重试也白搭。
  • 重试计数持久化：run_retry_attempts 表（count_retry_attempts，repository.py:1097-1103）—— 重启后计数不丢，不会无限重试。
  • 预算耗尽：不是失败，是 WAITING(BUDGET_EXHAUSTED) —— 等用户决定（executor.py:322-324）。
  • 配置里的 max_consecutive_failures = 3 与 max_run_duration_seconds = 3600 是 DataHarness 层的限制（第 04 课）。

6. 取消：意图与执行的分离

回顾第 05 课：request_cancel 只记意图。Worker 侧执行取消（executor.py:410-432）：

# 先终止外部副作用（沙箱），再提交终态；旧 worker 无法用旧 epoch 越过此提交。
if self._sandbox is not None and checkpoint is not None and checkpoint.sandbox_id:
    lease = await self._sandbox.connect(checkpoint.sandbox_id)
    await self._sandbox.terminate(lease)                    # ① 先杀沙箱
now = self._clock()
with self._store.unit_of_work(immediate=True) as uow:
    stored = uow.repo.get_run(claimed.run.id)
    updated = stored.value.cancel(now)                      # ② 再提交 CANCELLED
    result = uow.repo.save_run(updated, stored.version, "RUN_CANCELLED",
                               lease=claimed.lease, lease_checked_at=now)
self._cancel_task(result)                                   # ③ 任务跟着取消
if self._workspace is not None:
    self._workspace.cleanup_staging(result.project_id, result.task_id)  # ④ 清理未发布产物

顺序是纪律：先消除副作用，再落终态。已正式发布的产物保留，未提交的 staging 清理（ARCHITECTURE.md:495-497）。取消接口幂等（request_cancel 只在没有意图时写时间戳）。

7. 崩溃恢复全景

Worker 执行中崩溃（进程死、断电、蓝屏） │ ├─ lease 30 秒后过期（默认 lease_duration=30s，worker.py:168） │ ├─ 下一个 Worker claim_next_run 选中它：recovered=True，epoch+1 │ ├─ _recovery_decision： │ ├─ 有 checkpoint + 沙箱在 → RESUME_FROM_CHECKPOINT（续跑） │ ├─ 有 checkpoint + 沙箱没 → REBUILD_SANDBOX（重建续跑） │ └─ 无 checkpoint → START_FROM_BEGINNING（从头，但快照不变） │ └─ checkpoint 校验：digest 一致、快照一致，否则 PolicyDeniedError

关键保证：恢复永远使用原 ProjectSnapshot（ARCHITECTURE.md:483-484）—— 文件更新不会偷换 Run 的输入视图。而 checkpoint（第 08 课）保证「已完成的分析步骤不重跑」。

8. Worker 与健康汇报

Worker 由 cli.py:52 的 dataharness worker 命令启动，装配在 worker.py:116-125（build_local_worker）。它把 API 重启与任务执行解耦 —— API 进程不持有 Worker（worker.py:1-6），所以 API 重启不会取消正在跑的长任务。

监督健康文件 WorkerHealthWriter（worker.py:176-224）：只写 pid、owner、状态、活动 Run ID 的小 JSON（原子替换），不含任何业务内容。API 的 /diagnostics 只读这个投影（api/services.py:169-192）。注意区分两个「心跳」：这个文件心跳是给运维看的；SQLite 的 lease 心跳是并发安全机制。

小测验：Worker A 的 lease 过期后，谁可以执行这个 Run？

查看解析
claim_next_run 的条件 ②（store.py:50-57）：status='RUNNING' AND lease_expires_at <= now 的 Run 可被回收。新 epoch 使旧 Worker 的所有提交失效（fencing）。

查看解析
