Lesson 05 · 项目的核心数据结构

领域模型与状态机：不可变对象如何管状态

本课解剖 src/dataharness/domain/：为什么所有对象都 frozen？状态转移表怎么工作？不变量如何被强制？

1. 什么是领域模型

领域模型 = 用代码表达「业务世界里的概念和规则」。DataHarness 的领域是：用户有一个 Project，里面有文件；对 Project 发起 Task；Task 的执行是 Run；Run 里的分析动作是 Step；产出 Dataset/Artifact/Finding。

这条概念链对应的文件（domain/__init__.py 的导出）：

Project ── ProjectFile ── ProjectFileVersion ── ProjectSnapshot   (project.py)
Task ────────────────────────────────────────────────────────      (task.py)
Run ─────────────────────────────────────────────────────────      (run.py)
AnalysisStep ────────────────────────────────────────────────      (step.py)
Session ─────────────────────────────────────────────────────      (session.py)
Dataset / Artifact ──────────────────────────────────────────      (artifact.py)
Finding / FindingCandidate / EvidenceRef ────────────────────      (finding.py)
Lineage / ResourceRef ───────────────────────────────────────      (lineage.py)

2. 第一条铁律：domain 层是纯净的

domain/__init__.py 的 docstring 写得很明确（domain/__init__.py:1-5）：

本层定义纯领域模型…不 import FastAPI/PydanticAI/OpenSandbox/sqlite3/OpenTelemetry，不执行 I/O， 所有对象为 frozen 值对象/聚合。

这意味着：领域对象不知道 HTTP、不知道数据库、不知道模型、不知道沙箱。它只回答「状态是什么、允许怎么变」。

为什么要这样设计？

因为核心规则最怕被技术细节污染。状态机规则可以单独写 Hypothesis 属性测试（代码注释提到，domain/state_machine.py:4-7）； 以后换数据库、换 Web 框架，规则一行都不用改。这就是第 01 课说的「分层依赖朝一个方向」。

3. ID 即类型：NewType

所有标识符都是包装过的字符串（domain/ids.py:13-32）：

ProjectId = NewType("ProjectId", str)
TaskId = NewType("TaskId", str)
RunId = NewType("RunId", str)
SnapshotId = NewType("SnapshotId", str)
...共 12 种 ID

NewType 不会在运行时增加检查，但类型检查器（pyright）会防止你把 RunId 传给需要 TaskId 的函数 —— 这对一个几十个模块相互调用的项目极其宝贵：编译期就消灭一类 bug。生产 ID 的格式是 {前缀}_{uuid4().hex}（idgen.py:24-25），测试用确定性递增 ID（idgen.py:35-37）。

4. 状态机：用转移表而不是 if-else

Task 的状态定义（domain/task.py:20-26）：

TASK_TRANSITIONS: TransitionTable[TaskStatus] = {
    TaskStatus.QUEUED: frozenset({TaskStatus.ACTIVE, TaskStatus.CANCELLED}),
    TaskStatus.ACTIVE: frozenset({TaskStatus.WAITING, TaskStatus.COMPLETED, TaskStatus.FAILED, TaskStatus.CANCELLED}),
    TaskStatus.WAITING: frozenset({TaskStatus.ACTIVE}),
}

这是 邻接表：每个状态列出允许前往的状态。check_transition（domain/state_machine.py:21-44）检查一次转移是否合法：

def check_transition(table: TransitionTable[S], current: S, target: S, subject: str) -> None:
    allowed = table.get(current, frozenset())
    if target not in allowed:
        raise IllegalStateTransitionError(
            f"{subject} 不允许 {current.value} -> {target.value}，允许的转移: {…}"
        )

状态方法（如 Task.complete，domain/task.py:92-98）内部调用它：

def complete(self, at: datetime | None = None) -> Task:
    target = TaskStatus.COMPLETED
    check_transition(TASK_TRANSITIONS, self.status, target, "Task")
    return self.model_copy(update={"status": target, "completed_at": at or utcnow(), "updated_at": utcnow()})

看这个模式：校验 → 复制 → 返回新实例。旧对象完全不变，新对象是新状态。全部状态枚举和转移表：

聚合状态枚举（domain/enums.py）转移表位置

TaskQUEUED/ACTIVE/WAITING/COMPLETED/FAILED/CANCELLEDtask.py:20-26

5. 不变量：构造时就被强制

光有状态机还不够 —— 状态和字段之间还有一致性约束。Pydantic 的 model_validator 在对象创建的瞬间检查（domain/task.py:46-55）：

@model_validator(mode="after")
def _check_wait_reason_consistency(self) -> Task:
    if (self.status == TaskStatus.WAITING) != (self.wait_reason is not None):
        raise ValueError("WAITING 状态必须且只能带 wait_reason")
    if (self.prompt_ref is None) != (self.prompt_hash is None):
        raise ValueError("prompt_ref 与 prompt_hash 必须同时存在")
    return self

「WAITING 必须有 wait_reason」这类规则，在对象出生时就保证，不可能构造出「WAITING 但没有原因」的矛盾对象。Step 也有类似规则：FAILED 必须带 failure_kind（domain/step.py:41-48）。

6. 不可变性：三件套（领域层）

以 ProjectSnapshot 为例（domain/project.py:144-162）—— 这是全项目最重要的不可变对象：

class ProjectSnapshot(BaseModel):
    model_config = ConfigDict(frozen=True)          # ① 对象不可变
    id: SnapshotId
    project_id: ProjectId
    entries: tuple[SnapshotEntry, ...] = ()         # ② 成员是元组
    index_version: str | None = None
    dataset_version_ids: tuple[DatasetId, ...] = ()

    def ready_entries(self) -> tuple[SnapshotEntry, ...]: ...
  • ① frozen：无 setter，任何"更新"都报错。
  • ② 集合字段用 tuple 而非 list：list 可以 append，tuple 不行 —— 连嵌套结构都不可变。
  • ③ 语义：Snapshot 是 Run 的「数据视图」，创建后不可变 —— 文件后续更新不允许改变旧 Run 看到的输入。这是可复现性的根基（ARCHITECTURE.md:262-264）。

同样的不可变三件套在数据库层还有第二重保险（SQLite 触发器禁止 UPDATE/DELETE snapshot 表，storage/migrations/0001_runtime.sql:247-259）——第 06 课展开。

7. 两个特殊的领域设计

7.1 Finding 的两阶段提交流程

Agent 只能提交 FindingCandidate（候选结论），只有 Host 的验证门能把它变成正式 Finding（domain/finding.py:1-5, 42-69）：

class Finding(BaseModel):
    model_config = ConfigDict(frozen=True)
    id: FindingId
    candidate: FindingCandidate      # 包含证据列表，空证据直接构造失败
    status: FindingStatus = FindingStatus.DRAFT

为什么？因为「模型自说自话」不能算数 —— 结论必须先过 Host 的 ExecutionGate/IntegrityGate/EvidenceGate（第 12 课）。

7.2 取消的两阶段

Run.request_cancel() 只记录「取消意图」时间戳，真正的终态化由持有租约的 Worker 完成（domain/run.py:49-51, 117-143）：

def request_cancel(self, at: datetime | None = None) -> Run:
    """只记录取消意图；终态化由持有有效 lease 的 Worker 执行。"""
    if self.cancel_requested_at is None:
        return self.model_copy(update={"cancel_requested_at": at or utcnow(), ...})
    return self  # 幂等：已有意图则不重复

注释解释了原因：调用方线程不能和 Worker 的沙箱提交竞态。意图与执行分离，是并发安全的经典手法（第 11 课讲 Worker 如何响应它）。
