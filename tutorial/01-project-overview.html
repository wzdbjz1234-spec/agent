Lesson 01 · 先建立整体地图

项目概览：这个仓库是什么

读完本课，你将对「DataHarness 能干什么、代码怎么组织、怎么跑起来」有一个整体印象。

1. 一句话概括

打开 README.md 第一段（README.md:3）：

DataHarness 是一个本地优先的数据分析 Agent Harness：Project 文件在本地版本化保存，Task/Run/Step 状态写入 Runtime SQLite， 生成的 Python/SQL 只允许进入 OpenSandbox，模型请求统一经过 ModelGateway 的 secret/PII 边界。

拆开这句话，就是全项目的四个支柱：

支柱含义代码位置
本地优先持久化数据文件、任务状态、产物都在你电脑上（SQLite + 本地目录）src/dataharness/storage/、providers/workspace/
云端 LLM 驱动大模型负责理解问题、规划、写代码、组织回答src/dataharness/agent/、privacy/
隔离执行模型生成的代码只能在沙箱容器里跑，不能碰主机src/dataharness/sandbox/、providers/sandbox/
统一模型出口所有发给云模型的内容必须经过 ModelGateway 的隐私检查src/dataharness/privacy/gateway.py

2. 它解决什么问题

想象你有一堆数据文件（销售报表、PDF 文档、Excel 表格），想让它帮你做分析。你可以直接把文件丢给大模型聊天—— 但这样有几个真实的问题，DataHarness 逐个解决：

  • 文件太多、上下文装不下 → 先建 Project 库，把文件版本化保存，用全文检索（FTS5/BM25）按需取片段（第 07 课）。
  • 模型写的代码有风险 → 代码只在断网的沙箱容器里执行，只读挂载你的文件（第 10 课）。
  • 任务跑一半崩溃了 → 所有状态写入 SQLite，Worker 用租约（lease）机制恢复未完成任务（第 11 课）。
  • 担心把密码、隐私数据发给模型 → ModelGateway 拦截凭据、把邮箱手机号替换成占位符（第 09 课）。
  • 模型胡说八道 → 最终结论必须绑定可验证的证据，过三道验证门（第 12 课）。

3. 系统架构总览

这是 ARCHITECTURE.md 第 4 节（ARCHITECTURE.md:89-125）的架构图，先混个眼熟，以后每课都会回来对照：

用户 / 本地客户端（浏览器或 curl） │ HTTP，仅 127.0.0.1:8000 ▼ FastAPI（薄 API 层）──────────── api/ │ ├── ProjectService / TaskService / RunService ── orchestration/ │ └── Runtime SQLite ── 状态事实源 ├── ProjectCorpus ── LocalWorkspace + FTS5/BM25 ── projects/ + workspace/ ▼ PydanticAI Agent（唯一的 Agent）── agent/ │ tools: search_project / execute_python / execute_sql / ... ▼ ModelGateway ────────▶ 云端 LLM API（secret 阻断 + PII 占位） ▼ AnalysisRuntime ──▶ OpenSandbox（断网 Docker 容器，只读挂载 Snapshot） └── 执行 LLM 生成的 Python/SQL，产出 Dataset/Artifact/Finding

完整版见 ARCHITECTURE.md 第 4 节；模块依赖方向见第 5 节（api → orchestration → agent → domain + providers）。

4. 目录结构：跟着这个清单读代码

包体在 src/dataharness/ 下，模块即"分层"。对照 ARCHITECTURE.md:139-197：

目录职责（一句话）关键文件
api/HTTP 控制面：所有路由、错误映射、DTOapp.py、services.py
config.py读取 TOML 配置文件，Pydantic 校验config.py
domain/纯领域模型：Project/Task/Run/Step/Finding…project.py、task.py、run.py
storage/SQLite：迁移、仓储、事务、事件、队列repository.py、store.py
projects/ProjectCorpus：文件导入、提取、检索、快照corpus.py、extractors.py、index.py
orchestration/Task/Run 生命周期服务services.py
agent/PydanticAI Agent 装配、工具、Runnerassembly.py、tools.py、handler.py
privacy/凭据/PII 检测、占位映射、模型网关gateway.py、policy.py、detector.py
sandbox/沙箱协议与模型定义protocols.py、models.py
analysis/分析执行、发布、验证门、血缘runtime.py、verification.py
workspace/文件命名空间策略与发布桥protocols.py、bridge.py
providers/第三方 SDK 适配：OpenSandbox、OpenAI、SQLite 工作区sandbox/、model/、workspace/、durable/
skills/本地预装 Skill 的发现与激活registry.py
cli.py / launcher.py / worker.py命令行、一键启动器、Worker 装配—
核心设计原则：分层依赖只朝一个方向

依赖方向是 api → orchestration → agent/analysis/projects → domain + providers（ARCHITECTURE.md:128-137）。 domain 层不 import FastAPI、不 import 任何 SDK、不做任何 I/O —— 它只是纯数据结构 + 状态规则。 这保证了核心逻辑可测试、可移植。后面第 05 课会看到为什么这么重要。

5. 先跑起来看一眼

官方运行手册在 README.md 第 4–12 节。现在不需要理解细节，只需要知道有哪些入口（第 13 课会实操）：

uv sync --locked          # 安装依赖（uv.lock 是依赖事实源）
Copy-Item .\dataharness.example.toml .\dataharness.local.toml   # 准备本地配置
uv run dataharness check  # 校验配置
uv run dataharness run    # 一键启动 Sandbox + API + Worker（前台）
                          # 浏览器打开 http://127.0.0.1:8000

另外三个常用命令（src/dataharness/cli.py:44-68）：dataharness serve（只起 API）、dataharness worker（只起 Worker）、dataharness --version。

练习：验证你的地图
  1. 打开 ARCHITECTURE.md，找到第 4 节架构图，在图上把「浏览器 → FastAPI → Runtime SQLite → Agent → ModelGateway → OpenSandbox」这条链路描一遍。

  3. 回答下面的小测验。

小测验：谁负责执行 LLM 生成的代码？

查看解析
项目最核心的安全承诺：生成代码从未在 Host 执行（ARCHITECTURE.md:654）。 所有 Python/SQL 只交给 OpenSandbox 在 Docker 容器里执行（第 10 课详讲）。

小测验：项目状态（Task/Run/Step）的事实来源（source of truth）是？

查看解析
设计原则 3.3「状态显式持久化」（ARCHITECTURE.md:80-82）：对话历史和沙箱内存都不是事实来源。 这也是「API 重启、Host 崩溃都能恢复」的基础（第 11 课）。
