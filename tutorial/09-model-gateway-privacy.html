模型出口与隐私边界：ModelGateway

本课解剖 src/dataharness/privacy/：所有发给云模型的内容如何被检查、阻断、替换。这是「云模型驱动本地数据」的信任基石。

1. 问题的本质

DataHarness 的承诺（ARCHITECTURE.md:13-15）：

通过本地持久化、隔离执行、统一模型出口和敏感信息误传防护，使云端 LLM 能够可控地驱动本地数据分析。

注意它不承诺「业务数据绝不离开本地」—— 业务数据允许发给用户选择的云模型。它只承诺两件事：

  1. 凭据（密码/Key/Token/连接串）绝不发给模型 —— 发现即阻断整个请求；
  2. 常见 PII（邮箱/手机/银行卡/身份证）在云端视图中被替换成占位符 —— 本地数据不动，模型看到的是假值，工具调用回来时再恢复。

2. 唯一出口：ModelGateway

铁律（ARCHITECTURE.md:347-349）：主 Agent、Compaction、摘要器、Skill 选择器以及未来所有辅助模型调用，全部必须经过 ModelGateway。业务模块禁止直接调用模型 SDK。

ModelGateway.complete（privacy/gateway.py:36-48）是唯一入口：

def complete(self, task_id: TaskId, request: str) -> PreparedRequest:
    """在 Provider 调用前阻断 secret、占位 PII，且再次脱敏模型回复。"""
    prepared = self._policy.prepare_request(task_id, request)     # ① 出境前检查
    try:
        response = self._provider.complete(prepared.cloud_text)  # ② 只有脱敏文本发出
    except ModelProviderError:
        raise                                             # 稳定分类错误原样抛
    except Exception as error:
        safe = self._policy.sanitize_boundary_text(task_id, str(error), BoundaryKind.EXCEPTION)
        raise ModelProviderError(safe.cloud_text) from error
    return self._policy.sanitize_boundary_text(task_id, response, BoundaryKind.RESPONSE)  # ③ 回程再脱敏

三段式：出境前检查 → 只发送脱敏文本 → 入境（响应、甚至异常文本）再脱敏。模型回复里可能包含用户 PII（比如「你刚刚发我的邮箱是…」），所以回程也要处理。

3. 出境检查：PrivacyPolicy.prepare_request

privacy/policy.py:90-95：

def prepare_request(self, task_id: TaskId, text: str) -> PreparedRequest:
    """扫描新增请求；凭据 fail closed，PII 转为该 Task 专属的云端视图。"""
    entry = self._scan(task_id, text)
    if entry.secrets:
        raise SecretDetectedError(entry.secrets)          # 有凭据 → 整个请求报废
    return PreparedRequest(self._store.mask(task_id, text, entry.pii), self._audit(text, entry))
  • 发现凭据 → 抛 SecretDetectedError，请求根本不会发出。消息只含凭据类型清单（policy.py:14-20），不含原文。
  • PII → mask() 替换成占位符，同时产出审计元数据（PrivacyAudit：只有 hash 和种类计数，无明文，policy.py:34-42）。

4. 检测器：两种不同的扫描

4.1 SecretDetector —— 阻断型（detector.py:64-114）

保守的正则规则表（detector.py:71-104），识别 5 类：

类型示例特征
PRIVATE_KEYPEM 私钥块（-----BEGIN ... PRIVATE KEY-----）
CONNECTION_STRINGpostgres://、mysql://、redis:// 等连接串
PASSWORDpassword = xxx 赋值模式
API_TOKENapi_key=、sk-...、ghp_...、AKIA... 等
COOKIEset-cookie: / cookie: 头

扫描结果是不重叠的 SensitiveMatch(kind, start, end) 位置对 —— 代码不返回明文，只返回位置与类型（detector.py:106-114）。

4.2 PIIDetector —— 替换型（detector.py:128-170）

识别邮箱、手机号（中/美）、银行卡（用 Luhn 算法校验真实性，detector.py:117-125）、18 位身份证，还支持构造时注入自定义规则（CustomPIIRule，detector.py:49-52）。

为什么默认不识别姓名、地址这类 NER 型 PII？

因为「尽力而为」的分类可能误伤业务数据（ARCHITECTURE.md:363-364）。V1 只做可确定性验证的边界（ARCHITECTURE.md:86）：类型化、可逆、可测试的规则。

5. 占位符：可逆的云端视图

替换在 PlaceholderStore.mask（privacy/placeholders.py:144-158）：

# 每个值被替换成：<PII:{种类}:{序号}>，例如 <PII:EMAIL:0001>
placeholder = f"<PII:{kind}:{sequence:04d}>"

关键语义（ARCHITECTURE.md:367-373）：

  • 只在云端视图里改：本地 Dataset、Workspace 原样不动。
  • Task 内稳定：同一 Task 内同一值（规范化后）用同一个占位符 —— 模型才能理解「<PII:EMAIL:0001> 就是那个邮箱」；不同 Task 的映射互相独立，无法关联。
  • 规范化（邮箱小写、数字去格式）后查表复用（placeholders.py:99-106）。

映射存在哪？每 Task 一个独立 SQLite：runtime-data/privacy/{task_id}.db，表结构（placeholders.py:41-59）：

CREATE TABLE IF NOT EXISTS pii_mappings (
    placeholder TEXT PRIMARY KEY,
    pii_kind TEXT NOT NULL,
    normalized_hash TEXT NOT NULL,
    original_value TEXT NOT NULL,
    UNIQUE(pii_kind, normalized_hash));
CREATE TABLE IF NOT EXISTS scan_cache (...);

这个数据库的纪律（ARCHITECTURE.md:375-381）：不进 Workspace、不进沙箱、不进 Runtime DB、不进日志、不进 Artifact。它是与 Runtime DB 物理分离的第三个库。

6. 恢复：只在沙箱工具调用前

模型写代码时引用 <PII:EMAIL:0001>，执行前要还原成真邮箱。但不是无脑还原——restore_tool_input（policy.py:113-117）：

  • 只允许当前 Task 已登记的占位符；
  • 只允许 allowed_kinds 白名单内的类型（placeholders.py:160-181）；
  • 占位符未登记或类型不符 → PlaceholderRestoreError，拒绝执行。

为什么有白名单？防止模型「骗」系统恢复它不该用的类型（比如拿 EMAIL 占位符去套银行卡映射）。恢复后的代码才进入沙箱 —— 所以沙箱里执行的是真实数据，而模型永远只见过占位符。

7. 扫描缓存：内容寻址加速

每段文本都跑一遍正则会很慢。项目用内容 hash 缓存：scan_cache 以文本 SHA-256 为键缓存检测结果（placeholders.py:72-97），PrivacyPolicy._scan（policy.py:71-78）先查缓存。相同内容只扫一次 —— 和文件版本的 hash 思想一脉相承。

8. 审计：没有明文的元数据

每次出境的审计记录（PrivacyAudit，policy.py:34-42）只有：内容 hash、PII 种类与数量、secret 种类与数量。可观测性（OTel）也遵循同一纪律：message 属性必须经过 gateway.sanitize_trace 才允许记录（providers/observability/otel.py:138-154）。

9. 练习

练习：看检测器怎么工作
  1. 在 privacy/detector.py 里找出银行卡的 Luhn 校验函数（_luhn_valid），用几个真实卡号格式试推它的逻辑。
  2. 读 privacy/placeholders.py 的 mask，确认「同一 Task 内相同规范化值 → 同一占位符」的查表路径。
  3. 在 worker.py:135-142 找到 ModelGateway 的装配代码，复述三个组件的连接关系。
  4. 思考：模型回复里出现用户邮箱时，sanitize_boundary_text 会把它换成什么？它会被登记到映射表吗？读 policy.py:97-111 验证你的答案。
